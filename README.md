#### Kubernetes on Ubuntu virtual machines

Create a self-managed Kubernetes **1.36.4** cluster with one `control plane` VM and one `worker` VM, both running Ubuntu Server **24.04 LTS**.

This repository provisions instances on **GCP Compute Engine** and **AWS EC2**, using the same two Kubernetes node scripts on both providers.
Deploy the two nodes within the same cloud with private connectivity.

Azure provisioning workflow is not included in this repository yet.

This topology has one control plane and one workload node. It provides no control plane or workload high availability. 
Cloud load balancers, CSI storage drivers and cloud identity integration require additional components.

- For `AWS`, start with [setup_EC2.md](setup_EC2.md), then return here to initialize the nodes.

The `automation host` can be an Ubuntu 24.04 VM on any provider; it is separate from the two Kubernetes VMs and does not join the cluster.

- GCP uses `gcloud` directly. 
- AWS uses `AWS CLI v2` and `CloudFormation`, so the automation identity needs CloudFormation as well as EC2 permissions. 

Both workflows use private configuration and saved deployment state. AWS settings and state are separate from GCP's, allowing both workflows on the same automation host.

These scripts create fresh clusters; they do not upgrade existing installations.

The signed Docker repository supplies `containerd.io=2.3.5-1~ubuntu.24.04~noble`, including `runc`. The signed Kubernetes v1.36 repository supplies the exact Kubernetes
and cri-tools upstream versions; the scripts select the newest available Debian build revision for those versions. 

They stop if a required pin is unavailable. The `kubernetes-cni` dependency is resolved by APT; Cilium supplies the cluster networking implementation.

The six installed Kubernetes/runtime packages are held after installation. 
Installed package versions and the bundled `runc` version are recorded in `/var/lib/k8s-bootstrap/versions.txt`. 

Containerd configuration formats 3 and 4 are supported, including the format 4 generated by containerd 2.3.5. 
The scripts validate systemd cgroups and the pause image selected by kubeadm before starting the runtime.

#### Node prerequisites

Use fresh Ubuntu Server 24.04 LTS images with systemd, cgroup v2, Python 3. 
The node scripts accept amd64 and arm64. 

Start with at least **2 vCPUs, 4 GiB RAM and 30 GiB disk per VM**; allow additional capacity for your workloads and images.

After first-boot provisioning finishes, run on **each node** through SSH:

```bash
sudo cloud-init status --wait
sudo apt-get update
sudo apt-get upgrade -y
if [ -f /var/run/reboot-required ]; then sudo reboot; fi
```

Reconnect after a reboot before continuing. The bootstrap scripts stop if a reboot is pending. Run them after provisioning has finished, not from a cloud-init job that also waits for cloud-init.

#### Networking

Choose nonoverlapping `node`, `Pod` and `Service` ranges. The provisioning templates use these defaults:

| Setting | GCP | AWS |
| --- | --- | --- |
| Node subnet | `172.16.0.0/20` | `172.20.1.0/24` |
| `UNDERLAY_CIDRS` | `172.16.0.0/20` | `172.20.0.0/16` |
| `Control plane` private address | `172.16.0.2` | `172.20.1.10` |
| `Worker` private address | `172.16.0.3` | `172.20.1.11` |
| SSH login user | `k8sadmin` | `ubuntu` |

Both clouds use the following Kubernetes settings:

| Setting | Value or requirement |
| --- | --- |
| `POD_CIDR` | `192.168.0.0/16` |
| `SERVICE_CIDR` | `10.96.0.0/16` |
| `NODE_IP` | Required: this VM's actual private IPv4 address |
| `CONTROL_PLANE_IP` | Required on the worker; equals `NODE_IP` on the control plane |
| `UNDERLAY_CIDRS` | Required: space/comma-separated subnet, VPC/VNet, peering and VPN ranges relevant to the cluster |
| `ADMIN_USER` | Control plane only: sudo caller by default, otherwise root |
| `CILIUM_MTU` | Control plane only: `0` enables automatic detection |

The Pod range must contain at least two /24 node blocks. Supply identical Pod and Service ranges to both scripts. 

Use `ip -4 -brief address` on each VM to verify `NODE_IP`; a cloud public NAT address is not assigned to the guest interface.

Cilium uses Kubernetes IPAM, VXLAN encapsulation and IPv4 masquerading. Kubernetes allocates each node a /24 PodCIDR. kube-proxy remains in iptables mode. 
This configuration works without cloud-specific Pod routes, AWS ENI IPAM or Azure IPAM. [Cilium routing](https://docs.cilium.io/en/stable/network/concepts/routing/), [Kubernetes IPAM](https://docs.cilium.io/en/stable/network/concepts/ipam/kubernetes/)

MTU detection is automatic. If a VPN or network path needs a smaller MTU, supply the measured underlying network MTU using `CILIUM_MTU`; Cilium accounts for tunnel overhead. [MTU setting](https://docs.cilium.io/en/stable/helm-reference/)

#### Required ingress

| Destination | Protocol / port | Allowed source | Purpose |
| --- | --- | --- | --- |
| Control plane | TCP 6443 | Cluster nodes; optional trusted administrators with API access | Kubernetes API |
| Both nodes | TCP 10250 | Control plane | Kubelet API, logs and exec |
| Both nodes | UDP 8472 | Other cluster node | VXLAN |
| Both nodes | TCP 4240 and ICMP | Other cluster node | Cilium health checks |
| Both nodes | TCP 22 | Trusted automation host or administration network | SSH |
| Application nodes, if used | TCP/UDP 30000–32767 | Intended clients | Optional NodePort Services |

Apply the node rules in both traffic directions where relevant. 
- The bundled `GCP` workflow implements the first five rows using target/source tags and explicit SSH source CIDRs. 
- The `AWS` template implements them using security group references and `AWS_ADMIN_CIDR` for SSH.

Run `kubectl` over SSH on the `control plane`; public API and NodePort access require deliberate additional rules.

The worker does not need direct access to local etcd. Keep TCP 2379–2380 restricted to the control plane. 
Scheduler and controller-manager management ports do not require worker ingress. [Kubernetes ports](https://kubernetes.io/docs/reference/networking/ports-and-protocols/), [Cilium firewall requirements](https://docs.cilium.io/en/stable/operations/system_requirements/#firewall-rules)

#### Initialize the control plane

On the `control plane` VM, from the directory containing `k8scp.sh`:

**GCP defaults:**

```bash
sudo env \
  NODE_IP=172.16.0.2 \
  UNDERLAY_CIDRS="172.16.0.0/20" \
  POD_CIDR=192.168.0.0/16 \
  SERVICE_CIDR=10.96.0.0/16 \
  bash ./k8scp.sh
```

**AWS defaults:**

```bash
sudo env \
  NODE_IP=172.20.1.10 \
  UNDERLAY_CIDRS="172.20.0.0/16" \
  POD_CIDR=192.168.0.0/16 \
  SERVICE_CIDR=10.96.0.0/16 \
  bash ./k8scp.sh
```

Adjust the addresses for your own configuration. The script waits for `Cilium`, node `cp` and `CoreDNS`.

One Cilium operator replica allows initialization to finish before the worker joins. 

The `control plane` scheduling `taint` remains in place; normal application workloads run on the `worker`.

The script configures the sudo caller's kubeconfig with permissions 0600. If an existing default kubeconfig is present, it writes a separate file and prints its path. 

Follow the printed `KUBECONFIG` instruction when needed. If running as root directly, use `ADMIN_USER=your-login-name` to configure another existing account.

#### Prepare and join the worker

On the `worker` VM:

**GCP defaults:**

```bash
sudo env \
  NODE_IP=172.16.0.3 \
  CONTROL_PLANE_IP=172.16.0.2 \
  UNDERLAY_CIDRS="172.16.0.0/20" \
  POD_CIDR=192.168.0.0/16 \
  SERVICE_CIDR=10.96.0.0/16 \
  bash ./k8sWorker.sh
```

**AWS defaults:**

```bash
sudo env \
  NODE_IP=172.20.1.11 \
  CONTROL_PLANE_IP=172.20.1.10 \
  UNDERLAY_CIDRS="172.20.0.0/16" \
  POD_CIDR=192.168.0.0/16 \
  SERVICE_CIDR=10.96.0.0/16 \
  bash ./k8sWorker.sh
```

The worker script checks TCP/6443 connectivity and installs prerequisites. Its `worker.prepared` marker indicates completed preparation. 

`kubelet` may restart until `kubeadm join` supplies its configuration.

On the **control plane**, display the generated join command:

```bash
sudo cat /root/k8s-bootstrap/join-command.txt
```

Copy that complete command to the **worker** and execute it there. It includes the private API address, bootstrap token, CA public-key hash, containerd socket and `--node-name=worker`. 
Keep the join command private.

The token expires after two hours. Generate a replacement on the control plane if needed:

```bash
sudo kubeadm token create --ttl 2h --print-join-command
```

On the `worker`, run the new command with `sudo` and append:

```text
--cri-socket=unix:///run/containerd/containerd.sock --node-name=worker
```

Cilium's DaemonSet installs the worker agent after it joins. Helm, Cilium CLI and an administrator kubeconfig are needed only on the control plane.

#### Verify the cluster

On the `control plane`, as the `account` with the `administrator kubeconfig`:

```bash
kubectl wait --for=condition=Ready node/worker --timeout=10m
kubectl get nodes -o wide
kubectl -n kube-system get pods -o wide
cilium status --wait --wait-duration 10m

kubectl -n kube-system exec daemonset/cilium -c cilium-agent -- cilium-health status --verbose
```

Expect `cp` and `worker` to be Ready at `v1.36.4`, with the chosen private InternalIPs and `containerd://2.3.5`. 

The worker's ROLES column may show `<none>`; that is normal for a kubeadm-joined worker. Check `Cilium` cross-node host and endpoint health as well as node readiness.

#### Logs and recovery

| Path on a node | Contents |
| --- | --- |
| `/var/log/k8s-bootstrap-control-plane.log` | `Control plane` bootstrap log |
| `/var/log/k8s-bootstrap-worker.log` | `Worker` preparation log |
| `/var/lib/k8s-bootstrap/versions.txt` | Installed package versions and node settings |
| `/root/k8s-bootstrap/kubeadm-init.yaml` | `Control plane` configuration |
| `/root/k8s-bootstrap/kubernetes-images.txt` | Images selected by `kubeadm` |
| `/root/k8s-bootstrap/cilium-values.yaml` | `Cilium` values |
| `/root/k8s-bootstrap/join-command.txt` | Private `join` credential |

Read the first error and the corresponding log. On either node:

```bash
sudo journalctl -u containerd -u kubelet -n 150 --no-pager
sudo crictl info
sudo crictl ps -a
```

On an initialized `control plane`:

```bash
sudo env KUBECONFIG=/etc/kubernetes/admin.conf kubectl get pods -A -o wide
sudo env KUBECONFIG=/etc/kubernetes/admin.conf kubectl get events -A --sort-by=.lastTimestamp
sudo env KUBECONFIG=/etc/kubernetes/admin.conf cilium status
```

Completion `markers` are written only after the corresponding role succeeds.

- After a failure before `kubeadm` creates cluster state, fix the cause and retry with the same settings.
- After a partial `kubeadm init` or `join`, inspect the existing state; the bootstrap scripts refuse to overwrite it. They do not perform an automatic cluster reset.

- If initialization succeeded and `Cilium` installation alone timed out, resolve the network/image pull issue and resume that component:
```bash
sudo env KUBECONFIG=/etc/kubernetes/admin.conf helm upgrade --install cilium \
  /root/k8s-bootstrap/cilium-1.20.1.tgz \
  --namespace kube-system \
  --values /root/k8s-bootstrap/cilium-values.yaml \
  --wait=legacy --timeout 10m
```

Complete the readiness checks afterward. If the main script stopped before `configuring your kubeconfig` or creating the `join` command, 
use `sudo env KUBECONFIG=/etc/kubernetes/admin.conf ...` and create a fresh `join` command as above. 

Resuming one component does not complete the remaining bootstrap steps automatically.

#### Cleanup

From the `automation host`, follow the cleanup section of [setup_GCE.md](setup_GCE.md) or [setup_EC2.md](setup_EC2.md). 
Each provider's delete script `previews` its saved deployment by default; `--yes` deletes the nodes and their boot disks, including cluster data.

Cloud load balancers, dynamic persistent storage, cloud IAM integrations and a highly available control plane are outside this setup.

Deployments do not include a cloud controller manager, cloud CSI driver, or automatic cloud resources for a `Service` of type `LoadBalancer`.
